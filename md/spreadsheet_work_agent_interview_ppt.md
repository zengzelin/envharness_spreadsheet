## 0. 核心叙事：一条主线讲到底

按简历中的工作顺序讲：**Agent Harness → 数据合成与 SFT 设计 → GRPO 与 Reward → 结果与分析**。

> 让模型能够在真实工作簿上可靠执行，是后训练的前提；高质量示范教会操作习惯，环境奖励进一步优化任务完成。
> 当前已实现 Harness 和 GRPO，SFT 数据生产与训练方案已完成设计，后续按 Pilot 落地。

每部分回答一个问题：

1. Harness：怎样让表格修改可恢复、提交可校验、资源消耗可控制？
2. 数据合成与 SFT：怎样得到值得 Student 模仿的执行轨迹？
3. GRPO 与 Reward：怎样用最终工作簿结果优化模型，区分训练得分与任务成功？
4. 结果与分析：哪些能力改善，哪些语义错误仍然存在？

“工具执行成功 ≠ 任务完成正确”作为贯穿观点，用一个失败案例说明，不把主体讲成全部失败实验的时间线。

### P2 问题：为什么表格任务难（30 秒）

左侧一个真实任务截图：指令 + 工作簿 + `answer_position`。右侧四个风险图标：

1. 有状态二进制文件：半成品、损坏、pandas 重写丢样式；

### P4 Agent 闭环：检查—修改—重算—校验—提交

一张流程图（`SPREADSHEET_WORK_AGENT.md` 中的 mermaid 图），每个节点旁标对应工具：

- 检查：`list_sheets` / `inspect_range` / `find_cells`

### P6 执行预算：控制调用、修改范围与上下文开销

## 4. 高频追问 Q&A

### Harness 设计

**Q1：为什么要自己做 Harness，不直接让模型写 Python？**
A：纯 Python 方案下模型在简单的读操作上也要写 openpyxl 样板代码，错误非常多：`ws["C3:C6"]` 迭代得到 tuple、写合并单元格非左上角、凭指令猜 sheet 名。
结构化工具让模型只生成短参数，有 schema 约束和明确报错，写操作可以统一加锁、限额、原子提交。Python 保留为兜底。
工具消融中Python为104/399，Native Read为117/399，历史Native Basic为94/399。
这提示工具更多不自动带来更高成功率，完整工具的选择与组合还需适配；Read对Python的差异尚未统计显著。

**Q2：事务回滚具体怎么实现？为什么不让模型自己修？**
A：执行前把 output 复制成事务副本和备份，代码写事务副本；成功后检查是普通文件、openpyxl 能打开，再 `os.replace` 原子替换；失败或超时从备份原子恢复。
不让模型自己修，是因为半成品状态对模型不可见，它只看到报错，下一轮会在错误基础上继续叠加，模型的认知和文件真实状态就不一致了。

**Q3：提交门禁会不会让模型卡住提交不了？**
A：会有这种情况，所以单独统计了 `submit_gate_unrecovered`（被拒后再也没提交成功）。门禁拒绝时会告诉模型是“没校验过”还是“校验后又改了”，模型下一轮补一次校验就能提交。
NJ5 中 `no_submit` 从 24 降到 16。另外门禁会改变绝对分数，所以所有对比都在同一门禁配置下进行。
门禁保证显式Submit放行时版本已校验；达到步数上限仍会评分，没有提交会另记指标。

**Q4：50K/100K 是怎么定的？会不会误伤大表任务？**
A：先有事故，再统计日志：正常 format 最大 41,435 格；超过 5 万的 fill 只有 6 次，全是范围判断错误；10 万的单轮预算只拦过 70 万和 104 万格这类整列操作。
该组full-399中未触发累计预算限制，阈值覆盖已分析日志中的正常范围；还不能推广为所有大表任务零误伤。
真要支持几十万行，应做分块写入。

**Q5：为什么每轮最多 4 个调用？**
A：一轮一动作时，347/399 条撞 10 步上限，细粒度工具反而消耗轮次。4 能覆盖“读+写+校验”这类常见组合，同时控制单轮出错的影响范围和观察长度。
写类调用失败后短路剩余调用，避免在失败状态上继续修改。

**Q6：重算为什么限制每个 episode 1 次？**
A：这是初始吞吐与能力折中，LibreOffice启动有开销；一次额度不保证模型会在正确时机使用。
Step100重算后提交约0.25%，说明使用不足。后续用示范数据教闭环，并根据多次修复任务评估是否需要提高额度。

**Q7：LibreOffice 和 Excel 不一致怎么办？**
A：这是已知局限，新函数、动态数组、部分格式会有偏差。Spreadsheet-RL 原版用 Windows Excel 服务，成本是维护 Windows + COM。
我们的结论都标注为 LibreOffice 评测，跨论文对比时需要说明。

### 奖励与训练

**Q8：能否加入部分完成奖励？**
A：可以。当前采用官方二值主奖励，部分完成度尚未加入。历史Shaped Score包含执行惩罚，不能拿它证明部分分无效。
拟加入相对原始工作簿的完成度，减少全失败组缺乏区分的问题；先保留现有错误惩罚，只新增一个维度做消融。
需要处理原始文件已经部分正确、空目标和扫描截断，避免什么都不做也拿高分。

**Q9：执行惩罚会不会让模型变得保守？**
A：有这个风险。单次惩罚是−0.05/−0.1，但多次累计仍会影响轨迹排序，所以Checkpoint主要按任务成功率选择。
后续固定其余条件做惩罚消融，检查任务进度、探索和成功率；不能只看错误率下降就认为训练更好。

**Q10：GRPO 的 group 是怎么保证同任务的？**
A：worker 的 seed 是 `seed + i // group_n`，同一组 8 个 worker 拿到同一个任务索引，组内做优势归一化。

**Q11：训练中遇到过什么不稳定？**
A：早期 lr 1e-6 出现生成退化（大量乱码、无动作）；另一个 run 出现 KL 尖峰 7.5、训练成功率从 0.45 掉到 0.08。之后改为 lr 3e-7、KL 0.005。
还发现顺序取样在100步只覆盖前约1,600个任务位置，增加确定性Shuffle后取得了更好的单次结果。
两组实验有其他差异，Shuffle独立贡献需同配置开/关对照，第二Seed用于验证复现性。

**Q12：为什么 Step 110 会退化？**
A：训练后期 entropy 从 0.22 降到 0.10，inspect 使用减少，策略收缩；工具错误继续下降但公式结果错误上升。
这些是协议改善与语义错误持续存在的观测，尚不能确定唯一退化原因。
下一步核对Step100与110的任务回归，预先声明选点规则，检查Checkpoint选择偏差和策略收缩。

### 评测与结论可信度

**Q13：你怎么证明提升不是噪声？**
A：同一399条任务、固定Harness、确定性解码，Base失败Step100成功50条，反向25条，单次配对p=0.005228。
它支持本次配对差异，但尚未做跨Checkpoint选择的多重比较校正；当前只有单Seed，最佳点也是事后选出的。
后续预先声明选点规则并用第二Seed复现。

**Q14：为什么不用训练中的验证曲线选模型？**
A：64 条 fast-val 噪声太大，NJ5 的 fast-val 没有识别出 Step 100 的提升。早期 32 条上 step 5 领先 Base，到 399 条上反而落后。

**Q15：Verified 是 400 条，为什么你是 399？**
A：上游 Spreadsheet-RL 发行包里 verified 只有 399 个任务目录（缺 id=54675），README 写的是 400。我核对过下载日志和 zip 内容，不是下载丢失。
所有实验都用同一个 399 集合，内部比较不受影响，跨论文比较时需要注明。

### 开放问题

**Q16：如果继续做，你会怎么提升公式语义？**
A：三个方向：一是语义观察投影，按指令和 answer_position 把相关表头、公式、非空边界放进观察；
二是 Teacher 数据合成做 SFT 冷启动，示范“修改—重算—检查—提交”闭环；
三是对 `execution_clean_score_zero + formula_result_mismatch` 的任务做人工核对，先离线验证新信号与成功率的相关性，再考虑进入奖励。

**Q17：这个 Harness 能迁移到其他 Agent 任务吗？**
A：设计原则可以迁移：可信评测器定义成功、事务化的状态修改、版本绑定的提交、有界动作、多层诊断不改评分。
具体到代码 Agent 就是“测试通过才算成功、patch 原子应用、提交前必须跑当前版本的测试”。

**Q18：SFT现在做到哪一步？为什么和GRPO分开讲？**
A：已完成前七部分设计，包括API调度、轨迹转换、质量过滤、专项校验、LoRA配置及Checkpoint选择。
数据生产与SFT训练待实施。SFT教工具选择与执行习惯，GRPO用环境结果优化任务完成；现有29.82%来自Base直接GRPO。

**Q19：日志是不是完全不包含Python源码？**
A：Bridge/Worker常规执行日志只记摘要和长度，Trajectory保留完整动作；Trainer的评测样例展示仍可能包含代码。
这是执行日志降噪，不能称为全渠道脱敏。
